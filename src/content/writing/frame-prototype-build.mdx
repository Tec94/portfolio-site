## Frame

This is mostly me asking a lot of questions. What does the product need to do, who's using it, and what does "done" look like for you? Then I map out the steps someone takes through it and write down the constraints: your deadline, your budget, anything you already have that this needs to work with.

What you get: a short brief and a map of the main flows. {/* TODO: confirm the format. A doc? A FigJam board? */} If the brief makes it clear the project is bigger or smaller than we thought, this is the cheapest moment to change it, before anyone's paying for code.

## Prototype

I don't do long rounds of static mockups. {/* TODO: confirm this is true for how you work. */} I build the main interaction in code early, so you can click through it in a real browser, on your phone, with your own data if you have some.

I also build the messy states into it from the start. What does the screen look like when it's empty, when it's loading, when something fails, when someone does something weird? Those are usually where a product feels cheap, so I'd rather you see them now.

## Build

This is where the prototype turns into the real thing: the full implementation, tests, and a proper handoff. I write it so another engineer can pick it up without needing me around.

What you get: the code repository, a deployed version, and notes on how to run it, change it, and deploy it. {/* TODO: what else? A walkthrough call? A recorded video? A couple of weeks of fixes after launch? */}
